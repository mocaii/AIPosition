# AI POSITION 技术架构建议

> 历史方案，已被 Git 驱动方案取代。当前实现见 [docs/architecture.md](../docs/architecture.md)，不使用 CMS 或数据库。

日期：2026-09-15。本文为技术方案，未安装依赖或部署服务。

## 一、目标与默认选择

让编辑通过后台表单增加岗位、资料和关联，发布后公开网站自动更新。允许社区提交建议，编辑审核后进入正式知识库。

推荐采用一个 TypeScript 工程：Next.js 定制前台 + Payload CMS 管理后台/API + PostgreSQL 数据库。图片等资产进入对象存储。起步使用一个应用部署和一个数据库，定时任务处理链接检查；有明确性能需求后再拆独立 worker 或搜索服务。

Payload 提供管理界面、关系字段、认证、访问控制与草稿版本等基础能力；社区审核、链接去重与检查、发布联动仍需本项目实现。前台 UI 不受 CMS 后台外观限制。

## 二、系统分层

1. 公开前台：岗位浏览、技能专题、资料库、搜索、局部图谱。服务器渲染可索引正文；筛选、抽屉和图谱使用交互组件。
2. 编辑后台 /admin：岗位、技能、资料、板块、来源、投稿、核验记录。支持草稿预览、发布、回滚和归档。
3. 内容服务：校验、权限、去重、关系查询、审核、发布。Next.js 服务器端可通过 Payload Local API 调用同一套内容逻辑。
4. 存储：PostgreSQL 为唯一线上内容来源；图片和附件使用 S3 兼容对象存储；JSON 作为导入导出与版本化快照。
5. 后台作业：链接可达性检查、可选元信息抓取、发布后的缓存失效与重试。

## 三、内容模型

以下为逻辑实体，实际 SQL 表由 CMS 适配器和迁移管理，不假定 CMS 物理表名与此一致。

| 实体 | 核心字段 | 维护要点 |
|---|---|---|
| categories | name、slug、排序、简介 | 新增板块不改代码 |
| roles | nameZh、nameEn、aliases、slug、kind、summary、parent、category | 保留岗位实例、细分方向、职业和工种口径 |
| skills | name、aliases、slug、说明 | 岗位和资料复用同一技能记录 |
| resources | title、url、canonicalUrl、alternateUrls、类型、语言、难度、简介、前置知识、版本说明 | 一份内容只存一条，允许多个访问入口 |
| sources | title、organization、url、证据类型、核验记录 | 职位证据与学习资料用途分开 |
| submissions | 类型、目标 ID、建议内容、理由、提交者、状态、审核意见、baseRevision | 投稿与正式内容隔离 |
| users | name、角色、认证字段 | 初期只需编辑账号；社区登录后续按需要接入 |
| linkChecks | URL、检查时间、结果、HTTP 状态、跳转地址、错误类别 | 可达性检查与人工质量审核分开 |

### 关系

- 岗位 ↔ 技能：多对多，可带核心／补充属性。
- 资料 ↔ 技能：多对多。
- 岗位 ↔ 资料：多对多，保存推荐顺序、推荐理由、用途（入门／实践／深入）。
- 岗位 ↔ 来源：多对多。
- 岗位 → 父岗位：可为空，必须检测循环。

岗位—资料推荐可优先配置为岗位文档中的结构化关联数组，使顺序与推荐理由一起进入岗位草稿版本；数据库仍由适配器持久化关系。反向关联、图谱和数量从已发布内容计算，不手动维护两份。

需要独立大规模管理关联时再引入独立关系集合，同时设计关系的草稿发布与事务边界。

UUID 为内部稳定标识；保留现有 P001/R001 等为唯一 legacyId 以幂等导入。slug 用于可读 URL，改名不改内部 ID；slug 变动记录跳转。

## 四、日常维护体验

### 增加岗位

填写名称与别名 → 选择板块、口径和父岗位 → 填写简介 → 选择技能 → 从现有资料库勾选资料并排序 → 添加岗位证据 → 预览 → 发布。

不强制草稿完整。发布时执行必填与关系检查：岗位实例应有证据；编辑技能方向允许无招聘来源但必须标明口径。资料不足时可用明确空状态，不能凭空补充。

### 增加资料

粘贴链接 → 标准化并查重 → 可选抓取标题与描述 → 人工确认 → 填语言、类型、难度与推荐理由 → 关联技能和岗位 → 预览 → 发布。

已有链接时直接关联原资料。不同域名或镜像不自动认定重复，可由编辑合并并保留备用地址。

### 内容状态

编辑内容：draft → published，另有 archived 生命周期标记。已发布内容再次编辑保留公开版本，待新草稿发布后替换。

社区投稿：pending → accepted / rejected；可另设 needs_changes。通过后在事务中创建或更新正式内容、关系与审核记录。重试必须幂等，防止重复创建。

投稿针对旧版本时，比较 baseRevision，提示编辑处理冲突，不静默覆盖别人新提交的内容。Payload 草稿/版本是基础能力，完整社区审核流为自定义业务。

## 五、访问控制与内容边界

| 身份 | 权限 |
|---|---|
| 访客 | 读取已发布且未归档内容；向限流投稿接口提交建议 |
| 贡献者（可后续开放） | 投稿、查看和修改自己的待审核建议，无直接发布权限 |
| 编辑 | 编辑草稿、审核、发布、回滚与归档 |
| 管理员 | 编辑权限 + 用户与系统配置管理 |

匿名投稿初期只接收资料链接、推荐理由和关联目标，限制长度与频率；不允许匿名上传文件或直接调用内容写接口。

Payload Local API 默认可绕过访问控制。面向访客或投稿者的服务函数必须明确 overrideAccess:false，传入正确身份；公开查询还需限制发布状态。仅受控导入脚本和后台作业可显式提升权限。

公开详情、搜索、图谱、关联数量与导出必须应用同一发布过滤，不能通过关联展开泄露草稿。预览页鉴权且不进入共享缓存。

## 六、发布与页面更新

数据库提交完成后发送发布事件，失效岗位、资料、关联技能、搜索和首页相关缓存。事件持久化或记录重试状态，避免数据库已更新而页面长期陈旧。

关联资料改名、下架、改变核验状态也要刷新引用它的岗位页面与公开数量。删除优先使用归档；合并条目迁移引用并保留旧 URL 跳转。

Next.js 有按路径／标签重新验证机制，实施时按选定且与 Payload 兼容的版本使用对应 API。不以每次改资料都重新部署整个应用作为常规流程。

## 七、搜索与图谱

当前仅数百条内容，先使用数据库查询：中文名／英文名／别名／标题匹配，再按前缀、技能匹配和正文匹配排序。别名统一空格、大小写与全半角；中文短查询先保证简单包含匹配可用。

PostgreSQL pg_trgm 可辅助模糊匹配，但不等同于完整中文分词引擎，也不保证短查询命中效果。对中文、缩写、错拼做实际查询集验证；数据增长且相关性不足时再评估专用搜索服务。

搜索 API 返回岗位、技能和资料三个分组，携带各自分页与过滤条件。目录中没有可靠发布日期时不提供最新发布排序。

图谱由数据库关系生成有界节点和边，按板块和选中岗位逐步展开；不把全部关系一次加载到首页。图谱是视图，不必引入图数据库。组件库可在原型阶段按节点定制与无障碍需求评估。

## 八、资料链接检查

定时任务按 lastCheckedAt 分批检查，设置超时、并发限制和域名限速。记录 reachable、redirected、not_found、restricted、temporary_error 等结果。

403、429 和超时归为受限或暂时失败，不直接标为资料失效；反复 404/410 才进入人工处理队列。检查可达性不提升人工审核状态，不自动发布抓取摘要。

允许抓取任意用户链接时，阻止内网、回环、云元数据与非 HTTP(S) 地址；每次重定向重新检查目标，限制响应大小与超时。抓取内容作为不可信输入处理。

“内容发布状态”“入口可达状态”“人工审核状态”分别存储，避免把入口可读展示成质量认证。

## 九、部署与运营

推荐拓扑：HTTPS 反向代理／平台入口 → 一个 Next.js + Payload Node 应用 → PostgreSQL；媒体放对象存储。起步可用容器部署配托管数据库；具体服务商与地区待明确主要访客区域后选择。

本地与预览环境使用隔离数据库。生产数据库迁移纳入版本管理，在发布前检查；数据库自动备份并定期演练恢复。代码仓库和 JSON 导出不是数据库备份的替代。

密钥仅在服务端。记录应用错误、投稿审核操作与后台作业失败，不把用户信息或完整页面抓取内容写入公开日志。AI 标题/标签建议属可选功能，不成为基础维护流程的依赖。

依赖版本在实施时依据 Payload 安装兼容矩阵锁定，统一由 CMS 适配器管理数据库，避免额外 ORM 与其迁移相互冲突。

## 十、现有数据迁移

1. 检查当前 knowledge-base.json，记录导入批次与校验结果。
2. 按 categories → skills → sources → resources → roles 导入，创建 legacyId 到数据库 ID 的映射。
3. 第二遍补岗位父子关系、岗位技能和推荐资料，检测引用与循环。
4. 以 legacyId 幂等写入；默认仅新增或更新属于该导入批次的未编辑记录。人工编辑过的条目出现冲突时输出差异，不直接覆盖。
5. 保留原核验状态、采集日期、版本说明和口径；首次导入作为待审核草稿，可由编辑批量预览后发布。
6. 验证 80 个岗位条目、117 份资料、83 个技能、56 条来源、341 条推荐关系；线上可见数按实际发布状态计算。
7. 上线后数据库为主数据；旧 JSON 为原始研究快照，导出新的带时间戳快照用于备份辅助、审阅与可迁移性。

## 十一、实施顺序

第一阶段：内容模型、编辑账号、后台表单、关系管理、草稿预览、导入、发布与缓存更新。验收是编辑能独立新增岗位并在公开页面看到正确资料。

第二阶段：对照视觉稿实现岗位首页、详情、资料库、搜索和技能专题；所有内容来自 CMS。验证草稿隔离和移动端使用。

第三阶段：社区投稿、审核、冲突处理、链接检查和问题反馈。

第四阶段：局部图谱、批量编辑辅助、质量运营与可选 AI 标签建议。
